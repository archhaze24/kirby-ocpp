# OCPP 1.6J conformance notes

Coverage of `kirby-ocpp` against OCPP 1.6J. All 28 actions have schemas bundled in `crates/kirby-ocpp-core/schemas` (official Open Charge Alliance files, unmodified); the 11 actions of the OCPP 1.6 Security Whitepaper (edition 4, 2026-02-05) have typed messages and bundled schemas too (see Known limits). The station is an emulator for testing a CSMS, not a certified charge point; it is not OCA-certified and deliberately simulates hardware (no real metering, firmware or file transfer).

Legend: **full** = implemented as specified for emulator purposes; **partial** = implemented for common cases, see notes; **simulated** = the state machine and messages are real, the underlying action (upload, download, power flow) is not.

Validation: outgoing and incoming CALL and CALLRESULT payloads are validated against the schemas (the Rust build embeds them). An incoming CALL that fails validation gets a CALLERROR (unknown actions are answered with a CALLERROR). Behaviour is covered by the unit and integration tests in `crates/kirby-ocpp-core` and `crates/kirby-ocpp/tests`, driven by the in-process mock CSMS in `crates/kirby-ocpp-testkit`.

| Action | Status | Notes |

| FirmwareStatusNotification | simulated | Download/install lifecycle with selectable outcome and bounded retries. |
| Heartbeat | full | |
| MeterValues | full (simulated meter) | `MeterValuesSampledData`, `MeterValuesAlignedData`, `MeterValueSampleInterval`, `ClockAlignedDataInterval` honoured; values come from a simulated energy meter that follows the power model below. |
| StartTransaction | full | Reservation consumption, idTagInfo statuses. A non-`Accepted` `StartTransaction.conf` follows `StopTransactionOnInvalidId` / `MaxEnergyOnInvalidId` (see below). |
| StatusNotification | full | Fault metadata, `MinimumStatusDuration`, duplicate suppression. |
| StopTransaction | full | `StopTxnSampledData`/`StopTxnAlignedData` in `transactionData`, `StopTransactionOnEVSideDisconnect`. |

Transaction messages (`StartTransaction`, `StopTransaction`, `MeterValues`) are tried `TransactionMessageAttempts` times, `TransactionMessageRetryInterval` apart; CALLERRORs, timeouts and schema violations are retried, a lost connection is not. Transactions started or stopped offline are synchronised after reconnect, one entry at a time and in order. A queued `StartTransaction` or `StopTransaction` the CSMS still fails to process after those attempts is tried again while the connection is up (after `TransactionMessageRetryInterval`, at least 1 s), for at most `TransactionMessageAttempts` such retry rounds after the first failed one. After that a queued `StopTransaction` is dropped with a warning (the station gives up after its configured attempts; this also bounds what a hostile CSMS can leave in the queue), while a queued `StartTransaction` stays queued until the next connection because its transaction is still running. The queue holds at most 1000 entries: beyond that the oldest entry is dropped with a warning, entries without a pending start first. The queue survives restarts (see persistence in the README). A sync that is not the one after `BootNotification` (a retry round, a stop queued while online) delivers the entries only; the meter timers and the status re-send belong to the boot sync.

**`StopTransactionOnInvalidId` / `MaxEnergyOnInvalidId`** concern the `idTagInfo` of `StartTransaction.conf` (also for a transaction that was started offline and is synchronised later), not `Authorize`: an `Authorize` answered with anything but `Accepted` never stops a running transaction. When `StartTransaction.conf` carries a non-`Accepted` status: with `StopTransactionOnInvalidId=true` (default; the specification names none) the transaction ends at once (no local state, `StopTransaction` with `DeAuthorized`, outcome `TransactionRejected`); with `false` the transaction goes on and, if `MaxEnergyOnInvalidId` is above 0, is stopped with `DeAuthorized` once that many Wh have been delivered after the start (`0` = no limit). If the connector became `Faulted` or `Unavailable` while the `StartTransaction` was in flight, the transaction the CSMS opened is closed with `StopTransaction` (`Other`) and the start fails; the status is not overwritten with `Charging`.

**MeterValues sampling**: `MeterValueSampleInterval` applies for the whole transaction, also while it is suspended (`SuspendedEV`/`SuspendedEVSE`; the energy values just do not advance), and the timer runs for any interval (values above 86400 s are slept in several steps). The clock-aligned burst covers every connector, however many there are.

## Configuration keys

Registry keys, seeded from the station config: AllowOfflineTxForUnknownId, AuthorizationCacheEnabled, AuthorizeRemoteTxRequests, BlinkRepeat, ChargePointModel, ChargePointSerialNumber, ChargePointVendor, ChargeProfileMaxStackLevel, ChargingScheduleAllowedChargingRateUnit, ChargingScheduleMaxPeriods, ClockAlignedDataInterval, ConnectionTimeOut, ConnectorPhaseRotation, ConnectorPhaseRotationMaxLength, GetConfigurationMaxKeys, HeartbeatInterval, LightIntensity, LocalAuthListEnabled, LocalAuthListMaxLength, LocalAuthorizeOffline, LocalPreAuthorize, MaxChargingProfilesInstalled, MaxEnergyOnInvalidId, MeterValuesAlignedData(+MaxLength), MeterValuesSampledData(+MaxLength), MeterValueSampleInterval, MinimumStatusDuration, NumberOfConnectors, ReserveConnectorZeroSupported, ResetRetries, SendLocalListMaxLength, StopTransactionOnEVSideDisconnect, StopTransactionOnInvalidId, StopTxnAlignedData(+MaxLength), StopTxnSampledData(+MaxLength), SupportedFeatureProfiles(+MaxLength), TransactionMessageAttempts, TransactionMessageRetryInterval, UnlockConnectorOnEVSideDisconnect, WebSocketPingInterval; and the Security Whitepaper keys: SecurityProfile (writable, 0-3, can only be raised), AuthorizationKey (write-only), CpoName, CertificateStoreMaxLength (8), CertificateSignedMaxChainSize (10000), AdditionalRootCertificateCheck (false), and the edition 4 keys AllowSecurityProfileDowngrade (writable boolean, default `false`), AllowCentralSystemTLSWildcards (writable boolean, default `false`), CertSigningWaitMinimum (writable, seconds, default 20, values below 1 act as 1) and CertSigningRepeatTimes (writable, default 5). The whitepaper names no defaults for the last two; the values are this emulator's choice.

Capability and limit keys (for example `NumberOfConnectors`, the `*MaxLength` keys, `SupportedFeatureProfiles`) are read-only. Writable values are persisted per charge point. Some keys (for example `BlinkRepeat`, `LightIntensity`) are stored and reported but drive no behaviour. Vendor-specific keys are not supported (`NotSupported`).

## Testing aids (deliberate non-conformance)

Response rules (`--rule`, `KIRBY_OCPP_RULES`, TUI, scenario steps `set_rule` / `clear_rules`) make the station answer a CSMS command in a way the specification forbids, on purpose: `reject` (the action's rejection status, or CALLERROR `NotSupported` where the response has none: `GetConfiguration`, `GetLocalListVersion`, `ClearChargingProfile`, `GetDiagnostics`, `UpdateFirmware`), `delay:MS`, `error:CODE[:TEXT]`, `drop` (close the socket without a reply) and `ignore` (no reply, so the CSMS times out; the "every CALL gets one reply" rule is deliberately waived, bypassing the `InternalError` drop fallback). Without a rule the station behaves as described above. Rules are runtime only; except for `delay` the command is not executed. See the README for the syntax.

Local edits (TUI data browser, `Command::SetConfiguration`, `SetLocalListEntry`, `RemoveLocalListEntry`, `ClearLocalList`, `InstallChargingProfile`, `ClearChargingProfiles`) are not messages and have no spec equivalent; they reuse the rules of `ChangeConfiguration`, `SendLocalList`, `SetChargingProfile` and `ClearChargingProfile`. The local list version is the one thing they decide themselves: an edit is a differential update with version `current + 1` (a CSMS that tracks versions sees a mismatch, which is the point of testing it), and a local clear is a full update with an empty list and version `0` ("no list"). Nothing is sent to the CSMS after a local edit.

## Security Whitepaper behaviour (certificates, logs, extended trigger)

- **Certificate store**: Central System and Manufacturer root certificates (PEM, one per `InstallCertificate`, at most 5500 characters, at most `CertificateStoreMaxLength` = 8 in total). Only self-signed (root) certificates that are currently valid are accepted (subject equals issuer and the certificate's own signature verifies; no CA or basicConstraints requirement); anything else (garbage, expired, not yet valid, several certificates, not a root, store full) is `Rejected` (deviation: a full store is `Rejected`, as OCPP 2.0.1 says; the whitepaper text is ambiguous). Other signatures are not verified, except under `AdditionalRootCertificateCheck` (below). Installing a certificate that is already there is `Accepted` and changes nothing. Certificate hashes follow the OCSP CertID rules (hash of the issuer name DER and of the issuer key bits, serial in lowercase hex without leading zeros, compared case-insensitively); `GetInstalledCertificateIds` answers SHA-256 data, `DeleteCertificate` accepts SHA-256/384/512. With `SecurityProfile` 2 or 3 the last Central System root cannot be deleted (`Failed`). The whitepaper (edition 4) contradicts itself here: requirement `M04.FR.06` says that deleting the `CentralSystemRootCertificate` via `DeleteCertificate` SHALL answer `Failed`, while the remark of use case M04 says that deleting the last root is possible. The station follows `M04.FR.06` only for the *last* Central System root and only with `SecurityProfile` 2 or 3 (with profile 0 or 1, or while a second Central System root exists, the deletion is `Accepted`), which keeps a station from locking itself out of TLS; this is a choice, not a spec statement. With a fallback root present (below) deleting the new root is `Accepted` and the fallback becomes the normal root. Installed Central System roots become the TLS trust anchors (in addition to `--tls-ca`); once one is installed the system roots are no longer used (deliberate: with an installed Central System root, a server certificate chaining only to a system root is refused; delete the installed root to go back to the system roots). A `CertificateSigned` chain must be linked: each certificate signed by the next one (no trust anchor or name check).
- **`AdditionalRootCertificateCheck`** (`M05.FR.08` to `M05.FR.14`; read-only key, initial value from `--additional-root-certificate-check`, default `false`, so a CSMS cannot change it). `false`: the behaviour above. `true`: only one Central System root plus a temporary fallback exists. With no Central System root installed the first one is installed as above (self-signed). A new `CentralSystemRootCertificate` must then be currently valid, fit the size limits and verify against the public key of the installed root (signature checked with x509-parser); it need not be self-signed. If not, `Rejected` and nothing changes (`FR.10`). Otherwise it is installed, the old root becomes the fallback, an older fallback and any further Central System roots left from the time the check was off are removed, and the answer is `Accepted` (`FR.11`); the store must have room for the two entries, else `Rejected`. Installing a certificate that is present (root or fallback) is `Accepted` and changes nothing (`FR.14`). The fallback stays in `GetInstalledCertificateIds` and in the snapshot. It is not a trust anchor while the new root works: the first successful `wss://` connection (verification on, an installed Central System root in the trust set) after the install removes it (`FR.12`, persisted). If the TLS handshake fails because the server certificate is not valid for the trust anchors, the next reconnect attempt trusts the fallback instead (`FR.13`), and the next failure goes back to the new root; a connection made through the fallback does not remove it. Hash data of a root that is not self-signed names the certificate itself as its issuer (the real issuer's key is not kept; deviation from the OCSP `CertID` rules, only relevant for cross-signed roots). Manufacturer roots are not affected. Format version 5 added the fallback flag.
- **Certificate signing**: `RequestCertificate` creates an ECDSA P-256 key and a CSR (`CN` = charge point id, `O` = `CpoName` or `Kirby`) and sends `SignCertificate`. `CertificateSigned` is `Accepted` only if a request is pending, the chain parses, fits `CertificateSignedMaxChainSize`, every certificate is currently valid and the leaf carries the pending public key; otherwise it is `Rejected` and an `InvalidChargePointCertificate` security event follows. Chain trust is not verified. The leaf Common Name is not checked: `A00.FR.511` says the CN SHALL be the Charge Point's unique serial number (not a URL or IP address) and `A00.FR.405` has the Central System check it, but the whitepaper does not say that this equals the charge point identity, so the station does not enforce it (the CSR it creates uses the charge point id). **Back-off** (`A02.FR.17` to `A02.FR.20`, `A03.FR.17` to `A03.FR.19`): after a `SignCertificate`, if no `CertificateSigned` arrives within `CertSigningWaitMinimum` seconds the same CSR is sent again, then after twice, four times, ... that wait, at most `CertSigningRepeatTimes` repeats; then the station gives up until a new `RequestCertificate` or `ExtendedTriggerMessage` (`SignChargePointCertificate`) starts a fresh series. A `CertificateSigned` ends the series, also a `Rejected` one (`A02.FR.20`). Beyond the whitepaper text, a `Rejected` or timed-out `SignCertificate` answer is repeated the same way. If the timer fires while the station is not registered, the repeat is postponed by the same wait without being counted. The series is runtime state: a restart forgets it. A rejected or timed-out `SignCertificate` forgets its key and restores the previous pending key, unless a newer request has replaced it meanwhile (the whitepaper does not say what a new `SignCertificate` while one is open should do; requests are not refused). `ExtendedTriggerMessage` (`SignChargePointCertificate`) is implemented (see below).
- **Keys on disk**: certificates are public and live in the main state file (format version 8; older files load with an empty store, no fallback root and no previous certificate). The private key of the station certificate, the key of the previous certificate, a pending request key and the `AuthorizationKey` live in `<id>.station.secrets.json` next to it (mode `0600` on Unix, never in the main file, never in logs or the snapshot; GetConfiguration lists `AuthorizationKey` without a value and the snapshot shows `********`). The value of a `ChangeConfiguration` CALL for `AuthorizationKey` is replaced by `***` in recorded frames (station and CSMS: TUI log, `--json`, `--log-file`, history, scenario/script matching) unless `--show-secrets` is given; the wire is unaffected.
- **Profiles**: `SecurityProfile` can only be raised (lowering is `Rejected`), except that with `AllowSecurityProfileDowngrade` set to `true` profile 3 may be lowered to 2 (`A00.FR.005`, `A05.FR.01`, `A05.FR.10`; the key may be written at any time, and the lowered profile has to meet its usual prerequisites, a `wss://` URL and an `AuthorizationKey`). Lowering to 1 or 0 is never possible. 1 needs credentials (an `AuthorizationKey` or a password in the URL), 2 needs a `wss://` URL as well, 3 additionally a client certificate (`--tls-cert` or a stored certificate). After an accepted change of `SecurityProfile` or `AuthorizationKey`, and after `CertificateSigned` `Accepted`, the station sends the reply, then disconnects and reconnects at once so the new parameters are used (`A05.FR.06`/`FR.07`, `A02.FR.08`, `A01`; same wait for in-flight CALLs as a hard Reset, and it reconnects even with automatic reconnect off). Setting `SecurityProfile` to its current value is `Rejected` for 2 and 3 (`A05.FR.01`; no `AllowSecurityProfileDowngrade`), a no-op `Accepted` for 0 and 1, whatever `AllowSecurityProfileDowngrade` says. Not implemented: the fallback to the previous profile when the connection with the new one fails (`A05.FR.08`). Deviation: `A05.FR.03` (profile 2 or 3 needs an installed `CentralSystemRootCertificate`) is not enforced, because setups with a public CA (system roots, `--tls-ca`) are legitimate. Profile 1 and 2 send HTTP Basic Auth (user = charge point id, password = `AuthorizationKey` as given, 16-40 printable ASCII characters). Deviation: A00.FR.205 says the key is hexadecimal (up to 40 hex digits), but the whitepaper never says that the Basic Auth password is the decoded bytes, so the string is used as given and non-hex printable keys are accepted) unless the URL already carries a password; profile 3 uses the stored certificate unless `--tls-cert` is given. Profile 2 does not require TLS verification to be on. **Wildcard server certificates** (`A00.FR.308`, `A00.FR.510`): the station refuses a Central System certificate with `*` in a SAN DNS name or in the subject Common Name (a certificate that cannot be parsed counts as one) unless `AllowCentralSystemTLSWildcards` is `true`; the check runs after the normal verification, is raised as a certificate error (so `InvalidCentralSystemCertificate` follows, but the M05.FR.13 fallback root is not tried) and does not apply with `--tls-skip-verify`. The key is read when a connection is opened. Deviation: the Common Name is not matched against the FQDN (webpki checks the SAN and the name, as RFC 6125 does). **Old/new client certificate** (`A02.FR.28`/`A02.FR.29`, `A03.FR.24`/`A03.FR.25`, both SHOULD): when `CertificateSigned` replaces a certificate, the old chain and key are kept (the key in the secrets file; older state files load without them). With profile 3 the new certificate is tried first. A failed attempt switches to the other certificate, alternating for as long as attempts go on (the station never stops reconnecting). The switch is immediate after a refusal: a TLS alert about the client certificate (`BadCertificate`, `UnknownCA`, `CertificateExpired`, `CertificateRevoked`, `CertificateUnknown`, `UnsupportedCertificate`, `CertificateRequired`, `AccessDenied`, from the handshake or, with TLS 1.3, from the reading of the upgrade answer), an HTTP 401/403 answer to the upgrade, or a close or reset right after the TLS handshake. Any other failure (timeout, refused TCP, DNS, server certificate errors) switches after 3 consecutive failed attempts, so a short outage does not flip the choice constantly but a silent rejection is still covered; the counter is runtime state, reset on a switch and on a successful connection. Alternation only runs while a previous certificate exists (a renewal pending its first successful connection) and nothing is discarded without a successful connection. The first successful connection with the new certificate discards the old one; the first with the old one discards the new one (the old one is current again) and queues `DiscardedRenewedClientCertificate`. `--tls-cert` files take no part. The choice restarts with the new certificate after a restart. A second `CertificateSigned` before the first has connected keeps the oldest certificate as the previous one. An expired own client certificate is still presented (rustls does not check it; `A00.FR.431`), and the CSMS decides.
- **Security events**: sent as `SecurityEventNotification` once registered, queued offline (at most 100, persisted, oldest dropped; every event is kept, repeated identical ones too, except that `FailedToAuthenticateAtCentralSystem`, `InvalidCentralSystemCertificate`, `InvalidTLSVersion` and `InvalidTLSCipherSuite` raised by failed connection attempts are queued once per series of failures, which ends with the next successful connection (the whitepaper notes of `A00.FR.315`/`322`/`419`/`426` say once is enough); `Command::SendSecurityEvent` is never deduplicated; control characters in `techInfo` are replaced by spaces) and re-sent in order after the next accepted boot. Events stay in the persisted queue until the CSMS answered (a restart with a `SecurityEventNotification` in flight re-sends it). A CSMS answer with an error drops the event. Emitted: `StartupOfTheDevice` (once per process, after the first accepted boot), `ResetOrReboot`, `ReconfigurationOfSecurityParameters` (SecurityProfile/AuthorizationKey changes), `InvalidChargePointCertificate`, `FailedToAuthenticateAtCentralSystem` (HTTP 401/403 on the upgrade), `InvalidCentralSystemCertificate` (TLS peer certificate refused), `InvalidTLSVersion` and `InvalidTLSCipherSuite` (TLS handshake failures, mapped conservatively: alert `ProtocolVersion` or a server without TLS 1.2/1.3 is a version failure; alerts `HandshakeFailure` and `InsufficientSecurity`, no cipher suite or key exchange group in common are cipher suite failures; with mutual TLS a missing client certificate can also end in `HandshakeFailure` and is then misreported; the station cannot speak TLS below 1.2, so a server that only offers it fails this way too), `DiscardedRenewedClientCertificate` (see Profiles) and anything valid sent with `Command::SendSecurityEvent`. `SettingSystemTime` is not emitted because the station never sets its clock. `MaintenanceLoginAccepted` and `MaintenanceLoginFailed` (edition 4) are not emitted either, because there is no local maintenance interface; they can be sent with `Command::SendSecurityEvent` (the whitepaper recommends a `techInfo` like `{"user": "...", "origin": "..."}`).
- **Response rules** can target the four certificate commands (`reject` answers `Rejected`, `Failed`, `NotFound` and `Rejected` respectively).
- **GetLog / LogStatusNotification**: simulated, nothing is read or sent anywhere. `remoteLocation` must be an absolute URL with a host and scheme ftp, ftps, http, https or sftp, else `Rejected` (no `filename`). `Accepted` carries a generated `filename` (`diagnostics-log-<id>-<time>.log` or `security-log-...`; `logType` only changes the name). The reply comes first, then `LogStatusNotification` `Uploading` then `Uploaded` (100 ms apart) with the `requestId`; the diagnostics outcome knob (`SetDiagnosticsOutcome`) selects `UploadFailure` instead, with `retries` / `retryInterval` (at most 5 retries, at most 1 s apart) as for `GetDiagnostics`. A `GetLog` while an upload runs is `AcceptedCanceled`; the cancelled upload sends no further status (`UploadLogStatusEnumType` has no cancelled value; deviation: no `Idle`/other final report). A disconnect or `Reset` drops the remaining statuses. `PermissionDenied`, `BadMessage` and `NotSupportedOperation` are never produced. Snapshot: `log_status`, `log_request_id`.
- **ExtendedTriggerMessage**: same gate as `TriggerMessage` (only `BootNotification` before the station is `Accepted` or `Pending`, else `Rejected`; `connectorId` of `StatusNotification` / `MeterValues` must exist, else `Rejected`; it is ignored for the other messages). `BootNotification`, `Heartbeat`, `StatusNotification`, `MeterValues`, `FirmwareStatusNotification` behave as in `TriggerMessage` (firmware status is the current one). `LogStatusNotification` reports `Uploading` (with `requestId`) while a `GetLog` runs, otherwise `Idle` without `requestId`. `SignChargePointCertificate` is `Accepted` and starts the `SignCertificate` flow (as `RequestCertificate`). `NotImplemented` is never answered. The triggered message follows the reply.
- **SignedUpdateFirmware / SignedFirmwareStatusNotification**: simulated like `UpdateFirmware`; no file is fetched and the signature is never verified for real. The outcome comes from the firmware outcome knob (`SetFirmwareOutcome`, which gained `invalidSignature` and `installVerificationFailed`; a plain `UpdateFirmware` treats those two like `installationFailure`). Validation: `location` must be an ftp/ftps/http/https/sftp URL, else `Rejected`; `signingCertificate` must parse and be currently valid, else `InvalidCertificate` (plus a `InvalidFirmwareSigningCertificate` security event); if a ManufacturerRootCertificate is installed, a certificate of the PEM must be that root or have it as issuer (issuer name comparison only, no signature check), else `InvalidCertificate`; with no manufacturer root installed any valid certificate is accepted (assumption). `RevokedCertificate` is never answered (no revocation data). The reply comes first, then `SignedFirmwareStatusNotification` with the `requestId`: `[DownloadScheduled]`, `Downloading`, `Downloaded`, `SignatureVerified`, `[InstallScheduled]`, `Installing`, `InstallRebooting`, `Installed`. A retrieve or install time in the future adds the scheduled status and holds the next step (at most 1 s, as for `UpdateFirmware`). Failures: `DownloadFailed` and `InstallationFailed` repeat per `retries`/`retryInterval` (at most 5, at most 1 s apart); `InvalidSignature` (after `Downloaded`) and `InstallVerificationFailed` (after `InstallRebooting`) are final. `InstallRebooting` is only a status, the emulator does not restart; `DownloadPaused` and `Idle` reports are not produced by an update. Security events: `InvalidFirmwareSignature` on `InvalidSignature`, `FirmwareUpdated` after `Installed`. A request while a signed update runs is `AcceptedCanceled`; the cancelled update sends no further status (the enum has no cancelled value; deviation). A disconnect or `Reset` drops the remaining statuses. A signed update runs next to diagnostics and plain firmware plans (own queue). `ExtendedTriggerMessage` `FirmwareStatusNotification` sends a `SignedFirmwareStatusNotification` with the current status when the last update was a signed one. Snapshot: `signed_firmware_status`, `signed_firmware_request_id`.
- **Response rules** can also target `GetLog`, `ExtendedTriggerMessage` and `SignedUpdateFirmware` (`reject` answers `Rejected`).

## Security Whitepaper, CSMS side (`kirby-csms`)

The standalone CSMS answers the four charge-point security actions (`SignCertificate` with `Accepted`, the three notifications with `{}`), keeps the reports in the per-station state (last 100 security events, last log and signed firmware status, last CSR) and has typed commands for the seven CSMS actions. Connection security profile 1 and 2 check HTTP Basic Auth (user name must equal the station id; the password is compared byte for byte with the configured key, no hex decoding); profile 3 requires a verified client certificate whose subject Common Name equals the station id. The CSMS also keeps the last `GetInstalledCertificateIds` answer per certificate type (at most 64 hashes). It does not sign certificates itself, does not validate firmware signatures and does not enforce the whitepaper's certificate checks beyond what rustls/webpki verify.

## Known limits

- Security Whitepaper (edition 4, 2026-02-05), all 11 messages implemented. Implemented: `SignedUpdateFirmware`, `SignedFirmwareStatusNotification`, `GetLog`, `LogStatusNotification`, `ExtendedTriggerMessage`, `InstallCertificate`, `DeleteCertificate`, `GetInstalledCertificateIds`, `CertificateSigned`, `SignCertificate` (`Command::RequestCertificate`), `SecurityEventNotification` (`Command::SendSecurityEvent`), the security configuration keys and the profile 1-3 transport rules. See "Security Whitepaper behaviour" above.
- No OCPP 2.x, no JSON-over-SOAP; one WebSocket connection, subprotocol `ocpp1.6` by default.
- Meter, power, SoC and temperature values are simulated.
- Offline `MeterValues`: a sample of a running transaction that cannot be sent (the station is offline or not registered, or the transaction still has a local id because its start waits in the offline queue) goes to a separate persisted sample queue (state file `offline_samples`, format 8), bounded at 1000 samples (the oldest sample is dropped first, with a warning; start and stop entries are never touched). After the reconnect the samples of a transaction are sent with its real `transactionId`, in the order taken, after its `StartTransaction` was synchronised and before its `StopTransaction`; a sample stays persisted until its CALL ended, and one the CSMS rejects after the retry attempts is dropped with a warning. Samples of a transaction whose queued entry is dropped (rejected start, given-up stop, queue overflow) are dropped too. Samples without a transaction (idle connectors, clock-aligned) and samples taken while an online `StartTransaction` is still in flight are dropped.
- Diagnostics and firmware flows emit the right status sequences but transfer nothing.
- The simulated meter is deterministic: temperature and SoC are decorative functions of the energy.

- **GetCompositeSchedule bounds**: a `duration` above 7 days is clamped to 7 days and the reply carries the clamped `duration`; at most 1000 periods are returned (the tail is cut and `duration` ends where the first cut period would have started).
- **Connection limits**: every WebSocket write (frame, ping, pong flush, close frame) has a 10 s timeout; a peer that stops reading is treated as a lost connection (normal reconnect). Messages and frames from the CSMS are limited to 4 MiB. `call_timeout_ms` is at most 24 h (`ConfigError::TooLarge`).
- **WebSocketPingInterval** is initialised from `--ws-ping-interval` and read when a connection opens, so a change applies from the next (re)connect; `0` disables pings. State files older than version 6 stored an unused value for it, which is ignored on load.
- **Restored stops**: a `StopTransaction` that was in flight at a crash is restored with its recorded stop time and meter reading (format version 6; older files fall back to the restore time and the connector's meter) and is queued per connector, so connectors sharing one CSMS transaction id each deliver their own stop.
- **Secrets in schema errors**: schema violations of a `ChangeConfiguration` for `AuthorizationKey` never quote the value (generic messages), and `Debug` output of the configuration registry masks it.

## Intentional differences from the earlier TypeScript version

Strict boolean parsing and CLI > env > default precedence; `GetConfiguration` key limit; `TriggerMessage` reports the real diagnostics/firmware status and honours the registration gate; maintenance timers are cancelled on disconnect; `ChangeAvailability` on connector 0 also changes all connectors; the reply to a CSMS command is sent before follow-up messages; atomic, versioned state files (directory fsynced, long ids get a hashed file name, a `Scheduled` `ChangeAvailability` survives a restart) with `.bak` recovery; `LocalAuthorizeOffline` and `AllowOfflineTxForUnknownId` default to `true` (TS and the spec leave the default to the implementation; TS used `false`, which made the built-in `offline-sync` scenario fail on a stock station). Both stay writable via `ChangeConfiguration`.

### Power model and smart charging (differences from TS, spec behaviour wins)

- **Power and energy.** A `Charging` connector draws `min(nominal power, charging limit)`; energy is the integral of that power over monotonic elapsed time, integrated piecewise across schedule period boundaries and re-evaluated when profiles, status or transactions change. Nominal power, voltage and phases are configurable (`--nominal-power-w` 7200, `--voltage-v` 230, `--phases` 1; single phase 7.2 kW is about 31.3 A). TS added a fixed `2 * interval` Wh per tick and reported unrelated power values.
- **Readings** come from the same numbers: `Power.Active.Import` is the power, `Current.Import` is power / (voltage x phases), `Voltage` is the configured voltage, `Power.Offered` / `Current.Offered` are the limit in force (also when idle), `Energy.Active.Import.Interval` is the energy since the previous sample. The `MeterValues` command still adds its `wh_delta` to the register.
- **Limit resolution.** Profiles in `A` are converted to watts (`A x voltage x numberPhases`, `numberPhases` defaulting to and capped by the station's phases) before they are compared, so `A` and `W` profiles combine. Precedence per instant: the bound `TxProfile`, else the highest stack level of `TxDefaultProfile` (connector's own wins a tie with connector 0), then the minimum with `ChargePointMaxProfile`. The `ChargePointMaxProfile` limits the whole station, so it is split equally between the connectors that are charging; `GetCompositeSchedule` still reports it per connector.
- **Gaps (composite schedule).** A profile limits only the instants it covers. Where no profile covers an instant there is no limit, so the composite schedule always spans the requested window, starts at the requested time, and shows the station's nominal power (in the requested unit) for uncovered stretches. `Rejected` only if no profile of the requested unit covers any instant of the window. The earlier port shifted `scheduleStart` after a leading gap and ended the schedule at a later gap.
- **Absolute and recurring profiles without `startSchedule` and `validFrom`** count their schedule from the moment they were installed (state file version 3 stores `installed_at`; profiles restored from older files count from the restore time). TS anchored them at the composite request time.
- **Reset.** A Hard reset waits briefly for in-flight CALLs (the `StopTransaction`s), closes the WebSocket and reconnects at once, then boots again; a Soft reset reboots on the same connection (TS rebooted on the same connection for both).

## CSMS engine behaviour (`kirby-csms-core`)

- **Inbound validation** (`validate_inbound`, default on): every inbound CALL of a known OCPP 1.6J action is validated against the embedded schema; a violation is answered with a CALLERROR using the same code the emulator uses (`OccurenceConstraintViolation`, `TypeConstraintViolation`, `PropertyConstraintViolation`, `FormationViolation`) and is not tracked in the station state. The CALL and the CALLERROR are recorded in the history and events as usual. Order: scripted fault, then validation, then responder, then canned reply (a fault is deliberate misbehaviour and keeps priority). Unknown actions skip validation (custom responders keep working); actions a charge point may not send still get `NotSupported`. Switch off with `--validate-inbound false` to test firmware that sends slightly off-schema payloads.
- **Memory bounds and the registry**: records (state, history, counters) are never evicted; a station id stays until `CsmsHandle::forget` removes it, up to `max_stations`. Per station the history is bounded by `history_cap` frames and `history_bytes_cap` bytes (default 8 MiB; the oldest entries go first; one frame bigger than the cap is stored with its payload replaced by `{"truncated": true, "originalBytes": n}`), and `received_by_action` keys are at most 64 characters (longer action names count under `other`). The station limit is re-checked when the session registers; a connection that lost that race gets a close frame (1013) after the upgrade instead of HTTP 503. The default listener is unauthenticated (profile 0): anybody who can reach it can register stations, so use a security profile or a firewall.
- **Duplicate inbound CALL ids**: a CSMS CALL whose id is still being handled is ignored with a warning (the single reply goes out when the handler answers). Once it has been answered, the same id is treated as a new CALL and handled again. OCPP-J 1.6 defines no reply cache for retransmissions, so the station does not keep one.
- **Transaction messages that never get through**: `StartTransaction`, `StopTransaction` and `MeterValues` are retried `TransactionMessageAttempts` times, `TransactionMessageRetryInterval` apart. A start that still fails online is discarded (the connector returns to `Preparing`; the CSMS may keep an open transaction if it processed the request but its answer was lost), a failed stop is queued and re-sent after the next accepted boot, and the stop the station sends to close a transaction the CSMS opened for a tag it refused is not retried or queued. A retried `MeterValues` can arrive after a later sample, because later CALLs are not held back while it waits.
- **One outstanding CALL**: dropping the `call` future after the CALL was written keeps the slot until the station answers or the timeout expires; the next queued CALL waits.
- **Unknown actions**: a CALL with an action name that is not an OCPP 1.6J action gets CALLERROR `NotImplemented`; a known action a charge point may not send (for example `Reset`) gets `NotSupported`.
- **Ping watchdog**: the CSMS sends a WebSocket ping after `ping_interval` (default 30 s, `0` disables) without any message from the station, and drops the station with reason `PingTimeout` if nothing arrives within `pong_timeout` (default 10 s) after it. Any inbound message counts as life.
